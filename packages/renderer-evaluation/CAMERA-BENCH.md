Scope: the benchmark harness for the camera-controlled neural renderer

## 1. The evaluation principle (ADR-009/011)

A candidate is a Technology Plane entry: it enters through a versioned
adapter that declares capability, version, provenance, resource
requirements, execution requirements, license/commercial constraints,
failure semantics, and benchmark identity. No model name becomes domain
truth; the benchmark evaluates the ADAPTER over the frozen fixtures, never
the product contract.

Neural re-camera is primarily a REPLAY/HIGHLIGHT/CINEMATIC path
(ADR-011 constraint 8): live tactical remains procedural/real-time-first
until measured otherwise. This benchmark therefore targets the batch
(re-camera) surface only.

## 2. The fixture set (rights-honest)

- **Source clips**: the two gate-audit clips (R601/R602, CC BY-SA 4.0,
  provenance recorded in `docs/testing/mvp-reality-engine-gate-audit.md` —
  NO binaries committed to the repo; the harness resolves them from the
  operator's `gate-clips/` directory and REFUSES to run when they are
  absent, the same fail-loud posture as the detection benchmarks).
- **Camera paths**: generated by the Camera Director seam
  (`packages/camera-director`) — the camera INTENT source per ADR-011
  constraint 7 (models receive camera intent; they never decide world
  truth). The fixture matrix pins N deterministic camera paths per clip
  (orbit, dolly, pan, replay-angle) so camera-path adherence is measured
  against a KNOWN intent, not an annotated guess.
- **SWM snapshot/events**: the canonical model the batch pipeline
  materializes for each clip (the same `RenderRequest` inputs the
  procedural renderers consume — the candidate adapter translates to its
  own conditioning, never a second world truth).
- **Output profile**: one frozen profile per run (e.g. 640×360@24 h264 —
  the gate audit's own envelope) so byte-cost comparisons are
  apples-to-apples.

## 3. The metric implementations (per the frozen profile)

1. **camera-path-adherence** — the rendered video's recovered camera
   trajectory (via the repo's calibration/TvCalib-lineage tooling) vs the
   Director-issued path: per-keyframe pose error (position/rotation),
   endpoint drift, and smoothness of the realized path. Report: mean/max
   pose error + the adherence ratio (keyframes within tolerance).
2. **player-ball-identity** — entity identity stability across frames:
   re-detect entities in the OUTPUT video (`packages/perception-detection`
   + tracking) and measure identity switches, disappearance-without-event,
   and appearance consistency vs the SWM's known roster.
3. **temporal-consistency** — the existing
   `@sporta/renderer-evaluation` temporal harness (identity flicker,
   geometry drift, artifacts) applied to the OUTPUT frames: the same
   metrics the procedural renderers are held to (one measurement spine,
   no second standard).
4. **geometry-consistency** — the rendered scene's recovered geometry vs
   the SWM's canonical pitch frame (105×68 m): reprojection error of
   known landmarks (pitch lines, goals) and player ground positions.
5. **hallucinated-region-rate** — the fraction of output frames/pixels
   that depict content with NO basis in the source or the SWM (measured
   by consistency between the output and re-projected source regions;
   unseen-region coverage is measured SEPARATELY and honestly labeled —
   a novel view legitimately synthesizes unseen regions; hallucination is
   content that contradicts known geometry/entities).
6. **event-preservation** — the canonical events that occurred inside the
   rendered window are still observable in the output (goal/no-goal
   states, possession continuity per the SWM's event stream).
7. **generation-latency** — wall-clock per output second (and per clip),
   measured through the candidate's compute adapter (the W914 seam), cold
   and warm.
8. **generation-cost** — the metered cost units the compute plane reports
   for the run (the existing `usage.costUnits` surface), plus VRAM
   peak/requirements declared by the adapter.

Every metric reports exact measured values + the threshold verdict; no
metric silently degrades (the W503 harness's own discipline).

## 4. The harness stages

```
fixture-resolution → adapter-registration → run (per candidate × clip ×
camera-path, through the compute plane) → measurement (the metrics above,
over the run's frozen outputs) → report (BenchmarkRun/EvaluationReport per
the technology-plane contracts) → promotion review (HF015, Tech-Lead-owned)
```

- `fixture-resolution` refuses to run without the licensed clips (typed,
  loud) — the detection-benchmark precedent.
- `adapter-registration`: each candidate enters as a TechnologyProfile with
  license/provenance/execution requirements; the registry below is the
  DISCOVERY record, not production approval (ADR-011).
- `run`: dispatched through the Compute Broker as ordinary render jobs
  (BYOC or Sporta-managed GPU — the same W914 seam), so latency/cost are
  measured on the real execution path.
- `report`: reproducible (seeded, versioned fixtures, versioned adapters),
  with the failure envelope (refusals, OOMs, timeouts) recorded as
  first-class results.
